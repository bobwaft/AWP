# MEMORY

## Phase 0
- Toolchain: Bun 1.4, Rust stable, Biome (config scoped to apps/packages/registry/assets; never run it over `.claude/`).
- Dev in WSL2: `bun run dev` prints libEGL/MESA/ZINK warnings. These are WSL GPU noise, not app errors.
- Root `dev` runs `tauri dev` from `apps/desktop`; `beforeDevCommand` is that package's `vite` script.
- `engine:build` is a stub until Phase 2. `csp` is null in tauri.conf.json: harden later.
- CI runs `bun run check`, then `cargo fmt --check`, clippy and `cargo test` on windows-latest and macos-latest.

## Phase 1
- Tokens: `src/styles/tokens.json` is mirrored by `tokens.css`; `tokens.test.ts` checks they match and runs AA contrast. `lib/theme.ts` always resolves System to `data-theme=dark|light` (no duplicated media-query CSS). Tailwind utilities (`bg-bg-1`, `text-text-2`, `text-accent`) come from `@theme inline` in tokens.css.
- Light theme values were chosen directly (not via an Impeccable session) and recorded in DESIGN.md §4.1; added tokens `--accent-bright`, `--on-accent`.
- Spec/AA conflicts left as spec has them (need human decision): dark `--text-3` is 4.1:1 on bg-0; dark `--line-strong` is 1.8:1; dark `--danger` is 4.39:1 on bg-3.
- Settings live in localStorage (`awp.settings`) for now, not the app-data `settings.json` from ARCHITECTURE.md; swap when the engine/Tauri fs owns it. Display mode is stored but no effect until the 3D scene (Phase 14).
- Component tests use `// @vitest-environment jsdom` per file with @testing-library/react. Biome needs `css.parser.tailwindDirectives` for `@theme`.
- Mock stage states: `MOCK_PROJECT` in `lib/stages.ts` (current 4, stage 3 stale). Right panel is an empty hidden `<aside>` slot.

## Phase 2
- Protocol: `packages/protocol` holds zod envelope + `methods` (params/result) + `notifications`. Add new RPC methods to `methods`; the engine rejects methods missing there. Errors: JSON-RPC numeric `code` plus stable string in `error.data.code`. Only `ping`/`version` and `toast`/`engine.*` exist; the other ARCHITECTURE §4 methods are added by the phase that implements them.
- Engine: `createHandler` in `server.ts` is pure (line in, line out) and is what tests hit. `main.ts` logs JSON lines to `$AWP_LOG_DIR/engine.log` (Rust sets it to app-data `logs/`; Linux: `~/.local/share/dev.awp.app/logs`). Log rotation by date is not done.
- `bun run engine:build` compiles to `src-tauri/binaries/awp-engine-<triple>` (`--all` for all targets). Tauri's build.rs needs that file to exist even in dev, so root `dev` runs `engine:build` first and CI runs it before cargo. Binaries are gitignored.
- Rust supervisor (`src-tauri/src/engine.rs`): debug builds run `bun run packages/engine/src/main.ts`; release runs `awp-engine` next to the app exe. `engine_request` returns the full JSON-RPC response; engine notifications are re-emitted on `engine://event` as `{method, params}`; the supervisor itself emits `engine.restarted` / `engine.failed` (3 crashes in 60 s).
- Not verified: Windows (CREATE_NO_WINDOW path, `awp-engine.exe` kill test) and a release bundle; only Linux dev was exercised. Killing the engine in dev restarts it (checked by hand).

## Phase 3
- `AgentEvent`/`RunRequest` zod live in `packages/protocol/src/agent.ts`. RPC: `agent.run {prompt,cwd,adapter,model?,fixture?}` → `{runId}`, `agent.stop`; events stream as `run.event`. Server now passes the zod-*parsed* params to handlers (defaults apply).
- Claude stream-json facts (CLI 2.1.301): `system/init` has session_id+model; tool calls are `assistant` content `tool_use`; results are `user` content `tool_result`; final `result` has `usage` + `total_cost_usd`. Prompt is passed after `--` (tool lists would swallow it). `claude auth status` prints JSON with `loggedIn`. Parser: `adapters/claude-parse.ts` (pure; file_change is derived from successful Write/Edit calls).
- Fixtures `packages/engine/test/fixtures/claude-*.jsonl` are real transcripts (haiku), slimmed + scrubbed (paths → /work/project, user name, ids). FakeAdapter replays them through the real parser. The write fixture contains a denied Bash call, a realistic case.
- Stop: POSIX uses a detached process group + SIGTERM then SIGKILL after 2 s; Windows uses `taskkill /T /F`. Windows path is unverified.
- Dev screen: command palette → "Dev: run prompt". Verified a real Claude run through the engine over stdio (events streamed, done success). Stop was verified only on Fake + a process-tree unit test, not on a live Claude run.
- Tauri `invoke` of `agent.run` isn't covered by a UI-level test; `useRun` buffers events that arrive before the runId is known.

## Phase 4
- Detection (`packages/engine/src/setup.ts`) takes an injectable `Runner`, so tests never shell out. States: missing / needs_signin / outdated (Claude outside the tested range 2.1.x) / ready. Claude account+plan come from `claude auth status` JSON (`email`, `subscriptionType`). Windows: PATH is rebuilt from the registry via `reg query` (machine then user, %VARS% expanded) and passed to detection and to new PTY tabs (`setup.freshEnv`). Registry path is covered by a unit test with fake `reg` output only; not run on real Windows.
- Fix list is in `packages/protocol/src/setup.ts` (`FIXES`, per OS). Commands there are guesses to verify on Windows/macOS: `winget install --id Git.Git -e`, `irm https://claude.ai/install.ps1 | iex`, `curl -fsSL https://claude.ai/install.sh | bash`, `brew install gh`, `pip install semgrep`.
- PTY: `portable-pty` 0.9 (ConPTY on Windows). Commands `pty_spawn/write/resize/kill` are UI-only; `engine.rs` must never mention "pty" (Rust test enforces it) and the engine's callback handler only answers `secret.get`. Event names `pty://data/<id>`, `pty://exit/<id>`. Output is buffered per tab in `lib/terminal.tsx` so tabs replay when they mount. Output arriving between `pty_spawn` returning and `listen` registering can be lost.
- Keychain: `keyring` 3 (`linux-native` = kernel keyutils, not persistent across reboot on Linux; fine because Windows/macOS are the targets). Keys `awp/<service>/<account>`; names (never values) are listed in app-data `accounts.json`. Engine reads secrets via outbound RPC `secret.get` (`outbound.ts`); only `awp/` keys are served. Nothing calls `getSecret` yet; Phase 6/7 inject the Figma token into MCP config env.
- Engine now handles requests concurrently (no queue), replies are matched by id.
- Terminal ANSI palettes are hand-picked, not AA-verified. The drawer's drag handle is pointer-only (no keyboard resize). `Ctrl+\`` toggles the drawer; Setup shows the terminal inline and hides the drawer.
- Not verified here: a live PTY session in the running app (no display in this environment), Windows/macOS detection.

## Phase 5
- Protocol `project.ts`: `StageId` (10 ids, order = rail order), `ProjectState` (schemaVersion 1, `current` stage = where reopening lands, `stages.<id>.{status,criticRounds,override}`, `phases[]`, `updatedAt`). RPC: `project.create/open/list`, `stage.enter/complete/reopen`; notifications `state.changed` (full state) and `spec.changed {file}`.
- Orchestrator (`orchestrator.ts`) is pure and returns new states or throws `EngineError` (`STAGE_LOCKED`, `STAGE_NOT_ACTIVE`, `STAGE_NOT_COMPLETE`). Rules chosen: completing N activates N+1 only if it was locked; a `stale` stage is re-confirmed by `stage.complete`; reopening N makes later *completed* stages stale; `criticRounds` resets when the current stage changes. No gate on blocking questions yet (Phase 6).
- `EngineError(code, message, hint)` → JSON-RPC error `{code:-32000, data:{code,hint}}`.
- `ProjectService` holds one open project, persists `.awp/state.json` atomically (tmp + rename) after every mutation, keeps recents in `$AWP_DATA_DIR/projects.json` (Rust now sets `AWP_DATA_DIR` = Tauri app-data dir; logs go to `<data>/logs`). Spec watcher: recursive `fs.watch` on `docs/` (200 ms debounce) → `spec.changed`, then stale propagation via `stageForSpec`. AWP's own spec writes will also trigger it; harmless unless a later stage is already complete.
- Layout created by `project.create`: CLAUDE.md, MEMORY.md, BUGS.md (`- Status: open|fixed` lines are what "open bugs" counts), .gitignore, docs/, docs/design/, .awp/state.json; `git init -b main`, initial commit, then `awp/build` branch. Commits fall back to identity `AWP <awp@localhost>` only when the user has none configured.
- UI: `ProjectProvider` (lib/project.tsx) replaced the Phase 1 mocks (`MOCK_PROJECT` removed). On launch it reopens the most recent non-missing project. With no project the rail shows Setup current/done and everything else locked; locked stages stay view-only (`stage.enter` rejection is ignored). Setup completion is a localStorage flag (`awp.setupDone`). New: `Dashboard`, folder picker via `tauri-plugin-dialog` (capability `dialog:default`).
- Not verified: dialog picker in the running app, recursive `fs.watch` on macOS/Windows (Node supports it; tested on Linux only).

## Phase 6
- Architecture: `awp-engine mcp` is a stdio MCP *proxy* (official `@modelcontextprotocol/sdk`, low-level `Server`, JSON schemas from `z.toJSONSchema`). It forwards each tool call over a localhost HTTP bridge (`spec/bridge.ts`, random bearer token per engine process, `POST /tool`) to the main engine, so `ask_user`/`request_form` can block on the UI. Per-run MCP config is written to `.awp/runs/<runId>/mcp.json` (gitignored). `engineCommand()` picks `[execPath, 'mcp']` for the compiled binary or `[bun, 'run', main.ts, 'mcp']` in dev. `main.ts` is a dispatcher; the JSON-RPC server is `serve.ts`.
- Verified against real Claude Code 2.1.301 (haiku): the agent called `mcp__awp__ask_user` through the proxy and bridge, the answer flowed back, the synthesizer wrote `docs/PRD.md`, the critic called `submit_critique` (3 blocking, readiness 37). Dev override: env `AWP_MODEL` selects the model for spec runs until routing exists (Phase 10).
- Active MCP tools: ask_user, request_form, submit_critique, remember, approve_permission (wired via `--permission-prompt-tool mcp__awp__approve_permission`). The rest are registered in `mcp-tools.ts` and return `NOT_AVAILABLE`.
- `SpecSession` (`spec/session.ts`) = one per spec stage: chat, critique, pending question/form/permission, "Not sure" list, declined templates; persisted to `.awp/spec/<stage>.json` (forms in `.awp/forms/<id>.json`, pre-edit spec copy in `.awp/spec/<stage>.base.md` for the diff view). The UI is a pure view of `spec.state` snapshots (also `spec.get`). A user message runs interviewer → synthesizer → critic (critic only while `criticRounds < 3`; the counter lives in project state and resets when the current stage changes).
- Gate (`SpecService.checkGate`): needs ≥1 critic round, then zero blocking; after 3 rounds `overrideReason` (non-blank) completes anyway. A `stale` stage is re-confirmable without the gate.
- Forms: field subset schema is strict (`FormField` in protocol), `validateValues` lives in protocol and runs in both UI and engine (`FORM_INVALID` carries per-field errors as JSON in `hint`). Errors: `FORM_DECLINED`, `FORM_LIMIT` (one per turn), `FORM_SCHEMA_INVALID`. A form open when its run ends becomes an *orphan*; submitting it starts a new turn with the structured values.
- Prompts: Markdown-with-front-matter stored as TS string modules in `packages/prompts/src/library/` (works the same under Bun and Vite). Overrides: `.awp/prompts/<id>.md`. Form templates + `schemas/prd.sections.json` are real JSON files.
- Deviations / not done: (1) FormSummaryCard "Edit" reopens the form from the *submitted values*, not re-derived from the current spec text (hand edits are not merged), and resubmitting sends a chat message rather than showing a spec diff. (2) "Not sure" fields reach the critic prompt, but whether a blocking question is raised is left to the model. (3) Attachments are file paths appended to the message (no copy/analysis yet; image uploads arrive with Design). (4) Splitter and drawer drag are pointer-only. (5) `design_schema` template is Phase 7. (6) CodeMirror/diff UI is covered by logic tests with the editor mocked; not exercised in a live window.

## Phase 7
- The Design stage reuses `SpecSession` with `cfg.mode === 'design'` (`spec/config.ts`): the synthesizer slot becomes the **themer** (`submit_themes`), the critic only runs after a theme is picked, and `docs/DESIGN.md` + `docs/design/tokens.json` are rendered *deterministically by the engine* (`spec/design.ts`), not written by the model. `SpecPhase` gained `themer`; `SpecSnapshot` gained `themes`/`picked`.
- Flow: chat → interviewer → themer (once; `design.propose {feedback}` re-runs it) → user clicks a theme → `design.pickTheme` opens the `design_schema` form (engine-opened, prefilled from the theme, no agent waiting) → submit writes the docs, then `critiqueOnly()` runs the critic → normal gate. `pickTheme` with `tweaks` skips the form. Design-form submit is validated *before* the form is consumed (`DESIGN_CONTRAST` / `DESIGN_INVALID` leave it open).
- Contrast is enforced: `submit_themes` rejects any theme whose text/bg, text/surface, muted/bg or on-accent/accent pair is under 4.5:1 (`THEME_CONTRAST`), and the agent must resubmit. Verified live: real Claude (haiku) proposed 3 accepted themes. Density maps to base spacing (3/4/5 px) via `DENSITY_SPACING`.
- Refs: `design.addRef` copies png/jpg/gif/webp/svg/pdf (≤25 MB) into `docs/design/refs/` (de-duplicated names) or records http(s) links (Figma auto-flagged) in `docs/design/refs.json`; DESIGN.md lists them. Local file paths come from the dialog plugin in the UI.
- Figma: only if a token exists at keychain key `awp/figma/default` *and* a Figma link is in refs. The per-run MCP config references `Bearer ${FIGMA_TOKEN}` and the token goes only in the run's `env` (never written to disk; unit-tested). Server URL `https://mcp.figma.com/mcp` (REGISTRY.md); the Figma MCP's auth model with a plain token is unverified, since Figma's remote MCP normally uses OAuth through the user's Claude Code. Not exercised against a real Figma file.
- UI: `ThemesPanel` is an extra first tab in `SpecPanel` (`SpecStageView` in `IdeationView.tsx` is now generic over stage). Theme previews are `<iframe sandbox="" srcDoc>` (no scripts); font stacks are filtered to a safe charset. `FormCard` gained contrast readouts (color fields), font pairing preview, range sliders (number with min+max).
- Not done / limits: DESIGN.md hand edits are kept but not parsed back into tokens (tokens.json is only rewritten by a pick/form submit). Image refs are read by the agent via `Read`; vision quality unverified. "Mix themes" is covered only by tweaking the picked theme in the form.

## Phase 8
- Planning reuses `SpecSession` with `cfg.mode === 'planning'`. Prompt slots: `planning.architect` runs in the *interviewer* slot (it may ask constraints with `ask_user` / the `stack_constraints` form, then must call `submit_stack_options`), `planning.phaser` in the *synthesizer* slot (`submit_phase_plan`, busy phase `phaser`), `planning.critic` as usual. Flow: chat → architect → owner picks (`plan.pickStack`, optional verify-command edits + notes) → engine renders `docs/ARCHITECTURE.md` deterministically → phaser → critic. After a pick, chat messages are treated as feedback to the phaser (the architect is not re-run); `plan.propose` re-runs the architect (by sending a chat message).
- `packages/protocol/src/planning.ts` holds everything shared: `StackOption`/`Phase` schemas, `validatePhases` (needs title, goal, ≥1 task, ≥1 acceptance criterion, ≥1 checklist item, numbering 1..n in order), `renderPhasesMd`/`parsePhasesMd` (tolerant of hand edits: `[x]` ticks, any bullet, extra sections; round-trip tested), pure `movePhase`/`splitPhase`/`mergePhases`/`renumber`, `renderArchitectureMd`, `parseVerifyCommands`. Split copies acceptance + checklist to both halves; merge concatenates.
- Tool-side validation: `submit_phase_plan` rejects invalid plans (`PLAN_INVALID`) so the agent fixes and resubmits; `submit_stack_options` requires 2-3 options, each with all five verify commands. `plan.savePhases` (barrel edits) saves even when the plan is invalid and returns the errors (hand edits are never lost); the gate then blocks.
- Gate additions (`SessionPlan.planGateProblem`): Planning needs a picked stack and a PHASES.md that parses without errors. Also fixed a Phase 6 hole: `checkGate` now loads the persisted session, so a recorded critique still blocks after an engine restart.
- Verified live with Claude (haiku): options came back (3 stacks with their own test commands), pick wrote ARCHITECTURE.md, phaser produced a valid PHASES.md (scaffold phase first), critic reported zero blockers.
- UI: `PlanPanel` extra tab = `StackOptions` (side-by-side cards, editable verify commands, disabled when one is empty) + `PhaseBarrel` (list with up/down/split/merge, expandable details, "Edit as text" raw editor). The Connectors stage (5) is still the placeholder diagram, so the Phase 1 hotspot test now navigates to stage 5 first.

## Review of phases 3-8 (fixed)
- Fixed: answering `ask_user` while the run is busy (the UI blocked it and hung the run); forms leaking across stages (form files now record `stage`); lost updates in `ProjectService.mutate` (serialized + unique tmp file); `busy` claimed synchronously in `send`/`pickStack`; pending question/permission/form cleared when any run ends (`endBusy`); `pickTheme` refused while busy or an agent form is open; `scaffoldProject` commits only AWP's own paths and always appends `.env`, `.awp/runs/` to `.gitignore`; engine exits on stdin EOF; SpecPanel no longer clears "dirty" after a failed or stale save; corrupt `state.json` gives `STATE_INVALID`.
- Known and not fixed: sessions read the *current* project's state after a project switch mid-run; `byRun` ids are never forgotten; agent tool calls are not restricted to the calling phase's tools (`--allowedTools` only pre-approves) and `Read` is unrestricted; `remember` text is appended unsanitised; `docPath` does not resolve symlinks; `enterStage` resets `criticRounds` on every revisit (leaving and returning restarts the 3-round cap); `agent.stop` only reaches a cycle's first run; claude child processes survive an engine crash; terminal output between `pty_spawn` and `listen` can be lost, PTY listeners are never unlistened and exited PTYs stay in the map; bridge token compared with `!==`.
